# Test cases — DeckPlan v2

The contract is `docs/REDESIGN.md`. Every case marked `unit` needs a passing automated test: in Python (V1, `python3 -m unittest discover -s tests`, standard library only), then in Swift for the port (V2, `swift test` in `DeckPlanCore/`), both driven by the fixtures in `examples/`. `manual` cases go on `docs/DEVICE_CHECKLIST.md` (V3). Ids are stable: add, don't renumber. Field names follow the data as transcribed (`CURRICULUM_FORMAT.md` §3), not REDESIGN.md's shorthand where they differ (`DECISIONS_LOG.md` 2026-09-12).

**Group A (curriculum validation) is carried over from v1 unchanged**: A1–A14 in `docs/v1/TEST_CASES.md`, their tests in `tests/test_curriculum.py`, `test_assemble*.py`, `test_canonical.py`. They stay green throughout.

- `examples/class.stage1.json` — class `c-stage1-mw`, Stage 1, school age, N = 8, Mon/Wed from 2026-09-14, order 1, log entries for days 1–4 saved with the guide's own activities per block (28 ids: the fixture's done set), no draft.
- `examples/day-plan.stage1.day5.expected.json` — day 5 for that class and pool, canonical JSON.
- `examples/shuffle.stage1.day5.expected.json` — day 5's Warm-up trimmed to the guide's activities and shuffled twice (shuffle counts 1 and 2), and the Review shuffle, exhausted.

## P — Pool profile and filter (unit, V1)
- P1 Profile shape and defaults: `{ depths: {shallow, medium, deep}, diving, totDock, equipment: {<item id>: bool} }`, one key per *profile item* (P6, V5; V1 kept one per catalog item, never a `group`); a new profile has everything on. A missing profile key reads as off (so an item that becomes profile equipment later is off until toggled); a prop's key is ignored on read and dropped on write.
- P2 Equipment: an activity is hidden when any group in its `equipment[]` has no item on (`[["life-jacket", "float-belt"]]` passes with either on; `flotation-device` passes when any of its `anyOf[]` items is on); `equipmentOptional` never hides. Fixture (V5): with `kickboard` off, every activity whose only requirement is a kickboard is hidden, and every activity whose only requirement is optional, or a prop such as a life jacket, stays; the V1 fixture used `life-jacket` off.
- P3 Depth and diving: an activity with `depths` is hidden when none of its zones is on; no `depths` = never hidden by depth; `headfirst: true` is hidden when deep or diving is off. Fixture pool (shallow only): every `["deep"]` and `["medium", "deep"]` activity hidden, every dive hidden; turning deep on shows the deep ones but not the dives until diving is on too.
- P4 One filter everywhere: `pool_filter(activities, pool, catalog)` is the single function; the day plan, shuffle candidates, finder and browse produce no id it rejects (property test over the Stage 1 sample with the fixture pool and with everything off).
- P5 Age: the class's `ageGroup` maps to the tag P (preschool), S (schoolAge), A (teen, adult); `infantToddler` (Stages A, B) has no tag and the age filter is off; an activity with `ages: []` passes every age; one with `ages: ["P"]` is hidden for a school-age class. The finder without a class applies no age filter.
- P6 Profile equipment (unit, V5; DECISIONS_LOG 2026-09-12): `activities.profile_items(curriculum)` → the five catalog items that are the only option of a required group in the most activities of the loaded library, a `group` requirement counting toward each of its `anyOf` members, ties by catalog order, listed in catalog order; every other item is a prop. `is_on` is true for a prop whatever the profile holds; `normalize_pool` keeps one key per profile item and drops prop keys; the day plan, shuffle, finder and browse never hide an activity for a prop (P4's property test extended). Fixture: the Stage 1 sample's profile items are `pool-noodle, kickboard, hoop, small-toys, ball` (ball wins its tie with float belt by catalog order; in the manifest); with the full library (skipped without `curriculum/`) they are pool noodle, kickboard, hoop, small toys and pull buoy; `goggles` off in a profile hides nothing and is gone after a write.

## C — Classes, schedule, day numbering (unit, V1)
- C1 Create defaults: `lessons` 8, `ageGroup` the first of the stage's `ageGroups` (`preschool` for Stage 1), name "Stage 1 · Mon Wed" from the schedule's weekdays in week order, `order` = highest existing + 1 (1 when empty), empty log, no draft, a fresh id.
- C2 List order: by `order`, then `name`; two classes with the same order sort by name; renumbering after a delete is not required.
- C3 Delete: the class and its log (and draft) are gone; other classes untouched; nothing else in `classes.json` changes byte for byte.
- C4 Dates: `schedule.lesson_dates(first date, weekdays, N)` gives N dates in order; day k's date is the kth; Mon/Wed from 2026-09-14 → day 5 is 2026-09-28.
- C5 N ≠ 8: `session_plan.guide_lesson_mapping` unchanged (v1 B12): Stage 1 N = 6 → guide lessons 1, 2, 3, 4, 7, 8; N = 10 → 1–7, extra, extra, 8. An extra day takes guide lesson 7's block kinds and minutes with Review and Introduce `["any"]`, no guide activities, no topic.
- C6 Next day: no log → day 1; entries for days 1–4 → last done 4, next 5; an entry for a day > last done + 1 (an old re-save) still counts: entries {1, 2, 5} → last done 5, next 6; every day saved → last done N, next none, and the class is *complete*.
- C7 Today by date (unit, V5; DECISIONS_LOG 2026-09-12): `classes.day_on(class_, iso_date)` → the n whose schedule date (C4) is that date, else none; `classes.today(classes, iso_date)` → `[{classId, n}]` in class order for every class with a day on that date, done or not; `classes.next_lesson(classes, iso_date)` → the nearest `{classId, n, date}` on or after the date across classes, ties by order then name, none when every class is past its last date; `classes.missed(classes, iso_date)` → `[{classId, n, date}]` for every unsaved day dated before the date, oldest first, ties by class order. The Core takes the date as an argument and never reads the clock. Fixture: 2026-09-28 → day 5 of `c-stage1-mw`; 2026-09-21 → day 3, which is saved; 2026-09-29 → nothing today and next = day 6 on 2026-09-30; 2026-10-08 → nothing and no next. Missed: 2026-09-28 → none; 2026-09-29 → day 5 (2026-09-28); 2026-10-08 → days 5–8. The app no longer shows missed days: every day through today saves itself (D11).

## D — Today's plan (unit, V1)
- D1 Day k's blocks are guide lesson k's, in the guide's order (welcome, warmUp, review, introduce, topic, wrapUp), each with its `minutes`, `skillIds`, `stepRange`, `notes`, and the topic block with its `topicCode` and the topic's name and prompt. Fixture day 5: Welcome 2 · Warm-up 3 · Review 5 · Introduce 10 · Topic 5 (1.5) · Wrap-up 5.
- D2 Block candidates: the guide's own `activityIds` first, then the activities of the block's `skillIds` (each skill's `activityIds`), the whole list pool- and age-filtered, sorted by catalog order within the second part, duplicates removed (first occurrence wins). This is what Shuffle draws from and what Add is checked against; what a block *shows* is D10 (V5 — until V5 a block showed the whole list). Fixture: day 5 Review's candidates are its seven guide activities minus the hidden ones, then the rest of `1.front-float` and `1.back-glide`'s activities; the manifest holds the exact ids.
- D3 `["any"]` blocks: `skillIds: ["any"]` (Introduce in guide lesson 5, 6 and 8; Review in 6, 7 and 8) lists the stage's skills (library order, Greeting excluded) as `skillChoices` and shows no activities until the instructor picks one; picking `1.roll` makes the block behave as D2 with that skill. The pick is an edit (D6) and persists with the day.
- D4 Shuffle: on a block of any day, saved or not (DECISIONS_LOG 2026-09-13 "A day saves itself"), replace its activities with as many as the block shows now, drawn from the block's candidates (D2's full list before any edit) minus the done set of the class's other saved days (`classes.done_set(class_, n)`; for an unsaved day, the whole done set), walked as a cycle (DECISIONS_LOG 2026-09-13): the never-done candidates in a seeded order (seed = canonical hash of class id, day n, block kind; each candidate ordered by `canonical.hash_parts(seed, id)`), read from just after the last of the block's activities in that order (from its start when none is), the ones the block shows now taken only after every other (`day_plan.cycle_draw`). So a shuffle never gives back an activity the block shows while another never-done candidate is left, and repeated shuffles show every never-done candidate once before the first comes back. Same inputs → same draw; the shuffle count is still kept (the draft's `shuffleCounts`) but is no longer part of the seed. A block with no activities (D3 before a pick) is not shuffled. Fixture (V5): day 5's Warm-up, one activity shown (D10), shuffled twice; the manifest holds both draws, each a different never-done candidate. Unit: with one activity shown, one shuffle per other never-done candidate shows each of them once and never the one shown; the next shuffle shows the first again.
- D5 Shuffle exhaustion: fewer never-done candidates than slots → the block gets what exists and `message: "no more new activities for this block"`; zero → the block empties with the same message; none but the ones the block already shows → it keeps them, with the same message (DECISIONS_LOG 2026-09-13). A saved day shuffles like any other (DECISIONS_LOG 2026-09-13 "A day saves itself"): never done is in no saved day but that one, and the draw lives in the draft until the day is saved again. Unit: shuffling saved day 4's Warm-up draws a candidate no other saved day holds, not the one shown.
- D6 Edits: remove an activity, move one within a block, add one by id (from the finder); an added id not in the stage's library is refused. Edits, picks and shuffle counts live in the class's single `draft` `{ n, blocks: [{ kind, skillIds, activityIds }], shuffleCounts: {<kind>: int} }`; a draft for a day other than the next is dropped when the next day is opened.
- D7 Save: writes `{ n, date, blocks: [{ kind, activityIds }] }` to the class's log with `date` = the schedule's date for day n; clears the draft; day n is done. Re-saving a done day overwrites its entry; the log has one entry per n, sorted by n. The app has no Save button: D11 and every change to a saved day call it (DECISIONS_LOG 2026-09-13).
- D8 Revisit: opening a done day returns the saved entry's blocks (kinds and ids as saved, even if the pool now hides one — it is shown, flagged `hidden`); opening any day with a draft for it returns the draft (the working copy; `plan.draft` true), else the entry, else D1–D2's plan.
- D9 Determinism: the fixture's day-5 plan serialised with `canonical.dumps` equals `examples/day-plan.stage1.day5.expected.json` byte for byte and its SHA-256 the manifest's; the two shuffles equal `examples/shuffle…expected.json`. V2: Swift produces the same bytes.
- D10 The shown activity (unit, V5; DECISIONS_LOG 2026-09-12): a fresh block shows exactly one activity — the first of D2's candidates that is not in the class's done set; when every candidate is done, the first candidate; an `["any"]` block shows nothing until its pick (D3), then the same rule over the pick. The plan's `activityIds` is the shown list; candidates are not serialised. Save logs the one shown (D7), so the done set grows by one per block per day. Fixture: with days 1–4 saved (one id per block), day 5's Welcome, Warm-up and Wrap-up each show one id and Review one of its guide activities not yet done (Introduce is `["any"]` in guide lesson 5 and shows nothing until its pick); the expected JSON holds them. Welcome's three candidates were days 1–3, so day 5 shows the first again (`snowflake-welcome`, as day 4 did); the other three are not in the fixture's done set.
- D11 A day saves itself (unit, 2026-09-13; DECISIONS_LOG "A day saves itself"): `day_plan.save_through(curriculum, class_, pool, iso_date)` saves every day dated on or before the date that has no log entry, oldest first, each as D7 would (its draft when it has one, else its fresh plan with the days before it done), and returns the class, the days saved and the problems of a day it could not plan; a saved day is not written again; a draft for a later day stays. The Core takes the date and never reads the clock. Fixture (manifest `D11.saveThrough`): from the fixture class, 2026-09-27 → none; 2026-09-28 → day 5; 2026-10-05 → days 5–7; 2026-10-08 → days 5–8, with their entries. Unit: with a draft for day 6, saving through 2026-10-05 equals `save_day` of days 5, 6 and 7 in turn, day 6 saving the draft.

## F — Activity finder and browse (unit, V1)
- F1 Stage only: the candidate list is the stage's whole library (every skill's `activityIds` plus `greetingActivityIds`), pool-filtered, in a seeded order (seed = canonical hash of the inputs: stage, skill or null, step or null, age tag or null); page 1 is the first three, "three more" the next three, the last page possibly short; the page after the last is page 1 again, flagged `wrapped`. Same inputs → same pages. Fixture: 70 of the sample's 71 activities with the shallow pool (`volcano-ladder` hidden).
- F2 Stage + skill: only that skill's activities, same paging. Fixture: (1, `1.front-glide`) with the shallow pool.
- F3 Stage + skill + step: first the activities of every guide lesson block for that skill whose `stepRange` covers the step (guide order, deduped, only those the skill itself lists), then the skill's remaining activities; both parts pool-filtered, the first part in guide order and the second seeded. Fixture: (1, `1.front-glide`, 2): guide lessons 1–4 cover steps 1–4 → `puffin-rocket-ride, meteor-torpedo, comet-rocket-ride, jellybean-express` first.
- F4 Age: opened from a class → the class's age tag applies (P5); opened plain → no age filter; the fixture holds both for (1, `1.front-glide`).
- F5 Detail: name, description, required equipment as display names by group ("life jacket or float belt"), optional equipment, ages, `submerges`, and the title of each video whose `skillIds` includes the skill.
- F6 Browse: the stage's pool-filtered library grouped by skill in library order, each group's activities in catalog order, a Greeting group (`greetingActivityIds`) first; a skill with every activity hidden shows as an empty group.
- F7 Search (unit, V5; DECISIONS_LOG 2026-09-12): `finder.search(curriculum, stage_id, pool, text, age_tag=None)` → the stage's pool- and age-filtered library whose name contains the text, case- and diacritic-insensitive, grouped by skill as F6 (Greeting first), each group in catalog order; an empty or blank text → no groups; a text matching nothing → no groups. Fixture: (1, "glide") with the shallow pool → the `1.front-glide` and `1.back-glide` groups with their glide-named activities; (1, "GLIDE") the same; (1, "zzz") empty.
